## Context

See proposal.md (Why) for the motivation. This section covers only the current state that shapes the design, as read from the code at `2a81399`.

- Policy (`policy/policy.go`) is one Casbin `SyncedEnforcer` over `gorm-adapter`, loaded once at startup. The model is `r = sub, obj, act` with role inheritance `g = _, _`. The matcher allows role inheritance and also a direct `r.sub == p.sub` match. `/verify` calls `Enforce("device:<node_key>", "derp:default", "connect")`. After the registration transaction commits, `/register` writes `g, device:<node_key>, user:<user_id>` and `g, user:<user_id>, role:standard`. `Bootstrap` seeds `p, role:standard, derp:default, connect`. With `ENABLE_CASBIN=false` the engine allows everything and writes nothing.
- The verify cache (`service/cache.go`) is per process and keyed by node key, with epoch-based invalidation. `SetDeviceRevoked` and `SetUserDisabled` invalidate only the local cache.
- `/admin` (`server/admin.go`) is mounted when `ADMIN_API_KEY` is set. It checks one static bearer key in constant time, behind a single shared `rate.Limiter`. `/register` already uses a per-IP limiter (`server/ratelimit.go`) keyed by the TCP peer, because the router trusts no proxy headers.
- `db/migrate.go`: sqlite runs gorm `AutoMigrate` on the four models and ignores the SQL files. Postgres runs each `migrations/*.sql` once. Every new table therefore needs a model and a SQL migration, and any data upgrade must be idempotent Go code that runs on both.
- `audit_logs.device_id` has `ON DELETE SET NULL` only in the Postgres SQL. The `AuditLog` model declares no foreign key, so on sqlite nothing nulls it.
- derper (tailscale v1.84.3) POSTs `tailcfg.DERPAdmitClientRequest{NodePublic, Source}` to `--verify-client-url` with no identifying header. `--verify-client-url-fail-open` defaults to `true`.
- `config/config.yaml` ships `enable_casbin: true`, and `config/config_test.go` sets `enable_casbin: false`.
- Existing tests create users by SQL and expect `/register` followed by `/verify` to allow (`TestVerifyAllowUpdatesLastSeenAndAudit`, `TestAdminLifecycleEndToEnd`, among others). `TestVerifyPolicyDenied` inserts a device with no Casbin rules and expects `policy denied`.

## Goals / Non-Goals

**Goals:**
- Role-based, per-relay admission with Casbin, where the database is the only source of truth and every instance converges within a stated bound.
- Tiered, attributable admin access, with every authenticated mutation recorded atomically with its effect.
- An upgrade that keeps existing derper configs, admin callers and allowed devices working. A deployment with enforced policy needs no manual step; one that ran with policy disabled must say so once, at the first start.
- Keep the `/register` and `/verify` core logic and its tests. Only the changes named in the specs are allowed.

**Non-Goals:**
- Authenticating derpers to `/verify`. The relay name in the URL is trusted (decision B3).
- Deny rules, direct user grants, and an endpoint that explains a denial.
- Admin audit retention or pruning.
- A CI workflow, removing the empty `openspec/changes/refactor-derp-admit-layout` stub, and upgrading tailscale (needs Go 1.27.4). These are follow-ups.
- An automated end-to-end test with a real Tailscale client. Compose wiring is checked with `docker compose config` and a documented manual smoke test.

## Approaches

### Policy subject: per-device rules vs per-user subjects
- **Per-device rules (today).** Each registration writes `g, device:<node_key>, user:<user_id>`. Policy can then tell devices apart, but nothing uses that. Policy also duplicates the `devices` table, registration has a second, non-transactional write, and a device row with no rule is silently denied.
- **Per-user subjects (picked).** `/verify` already loads the device row, so its `user_id` is at hand. Enforcing `user:<user_id>` removes the duplicate state and the post-commit write, and the `devices` table stays the only device-to-user mapping. It loses per-device policy, which no decision asks for. Decided by the change author (decision A2).

### Cross-instance sync: periodic full reload vs version check vs LISTEN/NOTIFY
- **Periodic full reload (`StartAutoLoadPolicy`).** It is built in and simple. But every instance reloads the whole `casbin_rule` table every interval whether or not anything changed, nothing tells an instance that it is stale, and lifecycle changes (revoke, disable) do not live in `casbin_rule`, so cached decisions on other instances are not dropped.
- **Version check in the database (picked).** One cheap read per interval. A reload happens only when something changed. The same version covers lifecycle changes, so remote caches are dropped too. A failed read gives a clear staleness signal for the fail-closed rule. It works the same on sqlite and Postgres. The cost is that every decision-affecting write must bump the version in its transaction, and the staleness bound is the polling interval rather than immediate. Decided by the change author (decisions C1 to C5).
- **Postgres LISTEN/NOTIFY.** Near-immediate. But it is Postgres-only while tests run on sqlite. Notifications are lost while a connection is down, so a version check is needed anyway to recover. It also needs a dedicated connection outside gorm's pool.

### Relay identification: URL path vs query parameter vs separate listener or secret per relay
- **URL path, `POST /verify/:relay` (picked).** derper takes the verify URL as an opaque string, so any form that fits in a URL works. A path segment is visible in access logs and routing, cannot collide with other query parameters, and plain `/verify` maps cleanly to `default`. Decided by the change author (decision B1).
- **Query parameter, `/verify?relay=eu-1`.** It works equally well with derper. It is easier to drop by accident in proxies and URL rewriting, and less visible in route-level metrics.
- **Separate listener or shared secret per relay.** This would let the verifier authenticate which relay is calling. derper sends no headers, so the secret would have to sit in the URL anyway. That costs a listener or a secret per relay for a guarantee the owner did not ask for. Authenticating derpers is a non-goal.

### Admin key bootstrap: permanent root key vs import-on-startup bootstrap key vs separate enable flag
- **Permanent root key from env.** `ADMIN_API_KEY` stays an all-powerful key beside the stored keys. It is simple, but it cannot be revoked through the API, is not attributable, and defeats the tier model.
- **Import-on-startup bootstrap key (picked).** `ADMIN_API_KEY` keeps its two existing roles: it enables `/admin`, and it lets existing callers in. It becomes an ordinary stored key named `bootstrap`, so it is audited, revocable and covered by the lockout guard. Restarting with no active admin key recovers access. The cost is the three startup cases in `admin-access-control`. Decided by the change author (decision D3).
- **Separate enable flag** (for example `ADMIN_API_ENABLED`) plus a one-time key printed or created out of band. It is clean, but it changes every existing deployment's configuration, and it needs a second secret channel for the first key.

### A. Access model
- A1 Casbin stays. Roles decide connect, per relay. [OWNER]
- A2 The subject is `user:<user_id>`, resolved from the `devices` table. The object is `derp:<relay>` and the action is `connect`. Registration writes no rules, and legacy device rules are obsolete. [author]
- A3 Grants are role-level and allow-only, on named relays or on `*`. There are no direct user grants and no deny rules. Uncovered requests get `policy denied`. [author] Because the existing matcher also allows a direct `r.sub == p.sub` match, the builder must make sure only role grants can allow. [author]
- A4 `roles` and `relays` are registry tables (name, description, created_at), and names match `^[a-z0-9][a-z0-9-]{0,62}$`. Grants and bindings stay Casbin rules in their existing format: `p, role:<name>, derp:<relay>, connect` and `g, user:<id>, role:<name>`. [author] The `*` grant is stored as an `all_relays` flag on the role's registry row and expanded over the registered relays in memory when policy is loaded. It is never stored in `casbin_rule`, so no rule that exists before the upgrade, `derp:*` included, can act as a wildcard. Decided on 2026-11-23, replacing the earlier "builder's choice". [author]
- A5 Built-ins are relay `default` and role `standard`, with `standard` granted on `default`. They are seeded idempotently at startup and cannot be deleted (`409`). [author] The grant is seeded only when `standard` is created, so that edits to the grants of `standard` survive a restart. [author]
- A6 `POST /admin/users` binds `standard` when `roles` is omitted, and no role when `roles` is `[]`. A user with no binding fails closed. [author]
- A7 One-time upgrade, on both backends, in one transaction after seeding (A5), with a durable marker that prevents re-runs. It deletes no `casbin_rule` row. [author]
  - R1/S1 Invariant: no device that `POST /verify` denied immediately before the upgrade is allowed immediately after. A user is "covered on `default`" when, after the R4 import, the user has a managed binding `g, user:<id>, role:<name>` to a registered role that has a managed grant on `default`. No pre-upgrade rule can act as the `*` wildcard. Whether policy was enforced before is decided once, as in R1/S4. Not enforced: every user who is not covered is bound to `standard`, so every device allowed before stays allowed, and no device is revoked. Enforced: a user who is not covered and has no device rows is bound to `standard`, because the old version bound `standard` at first registration whatever other bindings the user had. A user who is not covered and has device rows is left as is and reported. Every non-revoked device without its registration rule (the canonical `g, device:<node_key>, user:<owner id>`, see R1/S4) is revoked and reported, whoever owns it and whatever the owner's bindings. The invariant concerns relay `default`, the only relay the previous version evaluated. [author] Revocation was widened from "covered on `default`" to "has a grant on any relay": rules naming other relays were dead data before, because the old version evaluated only `derp:default`, and importing them must not admit a device that was never properly registered. [author, 2026-11-23 review] It was then widened to every device without its legacy rule, whoever owns it: a user left without access kept devices that were never properly registered, and when an operator later bound that user to a role those devices would have been admitted, which is wider access than before the upgrade. Such a device stays revoked until an admin re-enables it. [author, 2026-11-24 fact-check]
  - R1/S2 Reporting: one warning with the ids and count of users left not covered, the ids and count of devices revoked, and the count of unmanaged rules. Devices that lose access only because rules outside the managed shapes stop granting are not listed: shipped code need not reconstruct the old model's per-device decision. Only `TestUpgradeNeverLoosens` does that. Each revocation gets an admin audit row with actor `system`. The admin audit table must therefore exist when the upgrade first runs (task 2.1). [author] In addition, the upgrade writes one info-level log line and one admin audit row with actor `system` and action `upgrade.run`, in its transaction. Its summary holds the mode and how it was determined, and the counts of users bound to `standard`, users left without access on `default`, devices revoked, unmanaged rules, and roles and relays imported, with no ids. A fresh database with no users gets the marker and no such row. Reason: the bindings to `standard` were neither logged nor audited, and the warning is logged once, by one instance, and is hidden at error log level. [author, 2026-11-24 fact-check]
  - R1/S4 The mode, enforced or disabled, is decided once, before the upgrade changes anything. This replaces the earlier rule, in which a boolean `ENABLE_CASBIN` decided the mode and the upgrade refused only when the setting was absent. [author, 2026-11-24 rehearsal]
    - A one-time setting `UPGRADE_POLICY_MODE` (env or `.env`) / `upgrade_policy_mode` (yaml) takes `enforced` or `disabled`, compared case-insensitively after trimming. Any other non-empty value fails configuration loading. Only the one-time upgrade reads it, and it has no effect once the upgrade has run. When it is set, it decides the mode and nothing else is consulted.
    - Without it, the mode is inferred from the data. The legacy setting (`ENABLE_CASBIN` / `enable_casbin`: false, true, or absent or not a boolean) is only a hint that must agree with the data. A non-revoked device "has its registration rule" when `casbin_rule` holds the canonical row `g, device:<that device's node_key>, user:<that device's owner id>`. A stale or non-canonical row (a non-canonical user id, a node key with no device row, a rule naming another user) does not count.
    - No non-revoked device: the upgrade runs as enforced. Nothing can be loosened or locked out.
    - At least one non-revoked device has its registration rule: policy was enforced. If the legacy setting is false, startup is refused, because the setting says disabled and the data says enforced, and "disabled" would bind every user and revoke nothing. Otherwise the upgrade runs as enforced.
    - Non-revoked devices exist and none has its registration rule: if the legacy setting is false, the upgrade runs as disabled. Otherwise (true, absent or not a boolean) startup is refused.
    - A refusal changes nothing: the upgrade's transaction is rolled back, and only the idempotent seeding of the built-in relay and role, done before it, stays. It writes no marker, and fails startup with an error that gives the number of non-revoked devices and how many of them have their registration rule, says which contradiction it is, and names both choices with their consequences: `UPGRADE_POLICY_MODE=disabled` binds every user who is not covered to `standard` and revokes nothing; `UPGRADE_POLICY_MODE=enforced` revokes every non-revoked device without its registration rule. A later start with the setting runs the upgrade normally.
    - The `upgrade.run` summary (S2) records the mode and its `mode_source`: `explicit`, `legacy_setting`, `data` or `empty`.
    - Reason: the old version wrote a registration rule at every registration while policy was enforced and none while it was disabled. The previous version's shipped `config.yaml` contains `enable_casbin: true`, so a leftover file is not a decision: in the rehearsal, a database that had run with `ENABLE_CASBIN=false` in the environment was started with the old yaml file and no env variable, the yaml value counted as an explicit "enforced", and every device was revoked. A leftover `enable_casbin: true` / `ENABLE_CASBIN=true` therefore never confirms anything, and the upgrade runs only once.
  - S3 When several new instances start at once against one database, schema migration, seeding and the one-time upgrade each take effect exactly once, and every instance starts. The mechanism is the builder's choice, for example a Postgres advisory lock around startup data changes, or relying on sqlite's `_txlock=immediate` serialization. This is separate from R6: mixed-version operation stays unsupported. [author]
  - R2 Legacy `g, device:*, user:*` rules are kept. They grant nothing in the new model, and are removed only when their device or user is deleted. [author]
  - R4 Every valid role name in `g, user:<uuid>, role:<name>` or `p, role:<name>, derp:<relay>, connect`, and every valid relay name in such `p` rules, is added to the registries. Every other rule stays in the table, never grants anything, and is counted in the warning. That includes direct `p` rules on `user:`/`device:`, other actions, invalid names, other grouping shapes, and a pre-existing `derp:*` object. The invariant is one-directional: devices allowed only by such rules become denied. Only the rule count is reported, not those devices (S2). Because of the `derp:*` case, the representation of the `*` grant (A4) must not let a rule that existed before the upgrade act as a wildcard. [author]
- A8 `ENABLE_CASBIN` is removed and ignored for enforcement with a warning, whatever its value and wherever it is set (env, `.env`, `config.yaml`). Failing startup instead would leave derpers on their default fail-open, which would admit everyone. [author] The one-time upgrade reads it only as a hint that must agree with the data (R1/S4), and startup fails at the first start only, when the hint contradicts the data or the data alone cannot tell and the hint is not false. Each configuration layer overrides the legacy value only when its own value parses as a boolean: an unparsable or empty value at a higher layer leaves a valid lower-layer value in place. The warning still fires whenever the setting is present. [author, 2026-11-24 rehearsal]
- A9 (R3) From this change on, the admin API is the only supported way to provision roles, grants, bindings and relays. A deployment without `ADMIN_API_KEY` can still insert users and tokens by SQL. Such users have no role and are denied until bound through the admin API. [author] Changing roles, grants, bindings or relays by SQL is unsupported. Such rows are picked up at the next policy reload on each instance, which happens at restart and whenever any admin change or new device registration moves the policy version, so they take effect at an unpredictable time, not only at restart. Without `ADMIN_API_KEY` there is no supported way to bind users to roles. [author, 2026-11-24 fact-check]
- A10 `casbin_rule` has the unique index `(ptype, v0, v1, v2, v3, v4, v5)` on fresh databases as well, created by the schema migration on both backends. Databases upgraded from the previous version already have it, because the previous version's Casbin adapter created it, so fresh and upgraded databases now have the same table. [author, 2026-11-24 rehearsal]

### B. Multi-relay
- B1 `POST /verify/:relay`. `POST /verify` means `default`. [author]
- B2 An unknown or malformed relay is denied with `unknown relay` in the normal response format, and audited. [author]
- B3 `/verify` stays unauthenticated, and the relay name is trusted as asserted (see Non-Goals). [author]
- B4 The cache key is (relay, node key). Verify audit rows record the relay in a new `audit_logs` column. [author] (R9) A name that matches the name format is stored as given, even when it is not in the registry. A malformed name is stored as null. Pre-upgrade rows hold null, with no backfill. The `relay` filter matches exactly. [author]
- B5 Checks run in this order: parse, relay known, registered, revoked, user disabled, policy. [author] The global verify rate limit stays in front of all of them, unchanged. [author, from the code] (S5/S6) Every deny produced after the rate limit is audited, including a body that is not valid JSON, which `server/router.go` answers today without an audit row. Rate-limited requests stay unaudited, as today, so a flood cannot fill the audit table. [author]
- B6 An empty relay segment (`POST /verify/`) or one containing `/` (`POST /verify/a/b`, `POST /verify/a%2Fb`) is a malformed relay name: the normal deny with `unknown relay`, audited with a null relay. `/verify/` is not redirected to `/verify`; only plain `POST /verify` means `default`. [author, 2026-11-23 review]

### C. Sync
- C1 The database is the source of truth. A stored policy version is bumped in the same transaction as each decision-affecting change. Each instance polls it every `POLICY_SYNC_INTERVAL` (default `2s`). The instance that made a change applies it before it responds. [author]
- C2 Role, grant, binding and relay changes reload the snapshot and drop all cached decisions. Device and user lifecycle changes and registrations drop cached decisions. [author] With a single version number, an instance that sees it move cannot tell which keys changed. The simplest catch-up is to reload and drop the whole cache, but the spec only requires the outcome. [author]
- C3 The bound: another healthy instance reflects a committed change within two sync intervals. [author]
- C4 Fail closed: after more than three intervals without a successful check, `/readyz` returns `503` and `/verify` returns `internal error`, including for requests that would be answered from the cache. [author]
- C5 Mechanism is the builder's choice. Options include writing `casbin_rule` rows through the same gorm transaction as the change and then calling `SyncedEnforcer.LoadPolicy`, or the adapter's `Transaction` / `NewTransactionalAdapterByDB` support, whose semantics have not been verified. The requirement is that the change, the version bump and the admin audit row are atomic. [author]
- C6 `POLICY_SYNC_INTERVAL` has a minimum of `100ms`; a lower value, zero or negative, fails configuration loading. With a tiny interval the three-interval staleness rule (C4) makes the instance permanently fail closed. [author, 2026-11-23 review]
- C7 Catching up does not deny. While an instance reloads because it saw a newer stored version, it keeps answering `/verify` from its current snapshot and `/readyz` stays `200`. It becomes stale only if the reload fails or C4 applies. The three-interval rule measures elapsed time, unaffected by wall-clock adjustments. [author, 2026-11-23 review] A reload that fails leaves the published version below the required one, so the instance is stale at once, without waiting for three intervals; the three-interval rule covers the case where the stored version cannot be read at all.

### D. Admin keys, tiers, audit
- D1 Stored, tiered admin keys replace the static key. [OWNER]
- D2 The `admin_keys` table holds id, unique name, tier, key hash, created_at, expires_at, revoked_at and last_used_at. A key is `dak_` plus base64url of 32 random bytes, and is stored as `hex(sha256(key + ":" + TOKEN_PEPPER))`. [author]
- D3 `ADMIN_API_KEY` enables `/admin` and is the bootstrap key (at least 16 characters). At startup: if `bootstrap` is active, its hash follows the env value; else, if no other active admin-tier key exists, `bootstrap` is created or reactivated; else the env value grants nothing and this is logged. Startup actions are audited as actor `system`. (R11) The name `bootstrap` is reserved: `POST /admin/keys` with it returns `409`. [author] The order of the three checks, treating an expired or absent `bootstrap` like a revoked one, writing no audit row when nothing changes, and treating a lost unique-name race between replicas as already done are additions. [author]
- D4 Revoking the last active admin-tier key returns `409`. Expiry can still leave none, and D3 recovers on restart. [author]
- D5 The tier matrix is as specified in `admin-access-control`. [author]
- D6 Every authenticated mutation is audited, including `403`. A successful mutation's audit row is written in the same transaction as the change. `401` is only logged and counted. Read-only requests are not audited. [OWNER wants everything audited and queryable; the details are the author's] `429` is treated like `401`, and failed mutations (`400`, `404`, `409`) are audited too. [author]
- D7 Audit queries are `GET /admin/audit/admin` (tier `admin`) and `GET /admin/audit/verify` (tier `viewer`), paginated newest first. [author]
- D8 The `/admin` limiter is per client IP, before authentication, keyed by the TCP peer. It keeps the `ADMIN_RATE_LIMIT_RPS` / `ADMIN_RATE_LIMIT_BURST` names. [OWNER for per-IP; the rest is the author's] It reuses the `/register` limiter type with its own instance. [author] The limiter type groups IPv6 peers by /64, for `/admin` and `/register` alike, because one host or site normally holds a whole /64 and per-address buckets would not bound it. Added on 2026-11-23 after a security review of the per-IP change. [author]
- D9 Startup never fails because `ADMIN_API_KEY` equals an existing key. When the configured value's hash belongs to a stored key other than `bootstrap`, startup leaves every key unchanged, logs an error naming that key (name and tier only), writes no audit row and continues. The configured value authenticates as the key it already is. This takes precedence over the three D3 cases. [author, 2026-11-23 review]
- D10 The key names `bootstrap` and `system` are reserved, compared case-insensitively after trimming: `POST /admin/keys` with either returns `409`. `system` is the actor name of startup audit rows, so a key named `system` would make audit rows ambiguous. [author, 2026-11-23 review]
- D11 The service writes no key hashes, token hashes or other bound query values to its logs, including the database driver's log of failed, slow or "record not found" statements. This was found in review. The token-hash case at `/register` existed before this change; the admin key case is new with stored keys. [author, 2026-11-23 review]

### E. Lifecycle API
- E1 `DELETE` for users (with their tokens, devices and bindings), devices and tokens. `200`, `404` and `400` as usual. [OWNER for scope; the details are the author's] Deletion must be explicit, in one transaction: delete the child rows, the `g, user:<id>, *` rules and the legacy `g, device:<node_key>, user:<id>` rules (R2), and set `audit_logs.device_id` to null, rather than relying on foreign-key cascades. sqlite has no `ON DELETE SET NULL` on that column, and does not enforce foreign keys unless `PRAGMA foreign_keys` is on. [author, from the code]
- E2 Revoke is a ban and delete is forgetting. [author]
- E3 A revoked node key of the same user gets `403` at `/register`. A node key of another user still gets `409`. [OWNER]
- E4 `limit` (default 50, max 200) and `cursor` on every list. `nextCursor` is null on the last page. Order is created_at ascending with an id tie-break, and audit lists are newest first. [OWNER for scope; the details are the author's] Roles and relays have no id, so they tie-break on name. Cursors are opaque, and an invalid one returns `400`. [author] A cursor is bound to the filter values it was issued under; sent with different filter values it is rejected with `400`, like a cursor from another list. [author, 2026-11-23 review]
- E5 User views carry `roles`. `PUT /admin/users/:id/roles` replaces them. [author]
- E6 and E7 Role and relay endpoints are as specified in `access-management-api`. (R10) `*` must be the only element of a `relays` list; mixing it with names returns `400`. [author]
- E8 A role or relay created through the API starts clean. Creating a role removes every leftover rule naming that role, and creating a relay removes every leftover grant naming that relay, in the same transaction; the audit summary reports how many rules were removed. This does not apply to the one-time upgrade's import (R4). [author, 2026-11-23 review]
- E9 A binding or grant cannot survive the deletion of its role or relay. When a role or relay is deleted while another request binds a user to it or grants it, afterwards no rule names a role or relay that is not registered. [author, 2026-11-23 review]

## Risks / Trade-offs

- [The upgrade revokes devices and leaves users unbound (R1).] Devices that were `policy denied` stay denied, now as `revoked`. Devices allowed only by rules outside the managed shapes (R4) become denied without being listed; only the count of such rules is reported (S2). → Users left not covered and revoked devices are reported in one startup warning with ids, revocations are audited as `system`, and one `upgrade.run` audit row and info log line carry the counts. The README upgrade notes tell operators to review the warning and re-enable or bind through the admin API.
- [A deployment that drops `ENABLE_CASBIN=false` before the first start, or keeps the old `config.yaml` with `enable_casbin: true`.] If no non-revoked device has its registration rule, startup refuses until `UPGRADE_POLICY_MODE` is set (R1/S4); a leftover `true` confirms nothing. → The README upgrade notes say to keep `ENABLE_CASBIN=false` or set `UPGRADE_POLICY_MODE=disabled` for the first start when policy was disabled, and the refusal message names both choices.
- [A mixed-history database, one that ran both with and without policy.] Registration rules exist, so without `UPGRADE_POLICY_MODE` it is treated as enforced: users with devices who are not covered stay denied, and devices registered while policy was disabled, which have no registration rule, are revoked. If `ENABLE_CASBIN=false` is still configured, startup refuses instead. → The operator can state `UPGRADE_POLICY_MODE=disabled`, which is looser: it binds every user who is not covered to `standard` and revokes nothing. Revoked devices can be re-enabled through the admin API.
- [Devices registered after the upgrade are denied by the previous version.] See Migration Plan, Rollback.
- [Per-IP admin limiting weakens the brute-force bound.] Under a shared bucket, key guessing was bounded in total. Per IP, it is bounded per source address. Generated `dak_` keys carry 256 bits, so this does not matter for them. The operator-chosen `ADMIN_API_KEY` only has to be 16 characters long. → Mitigation: the README recommends a high-entropy `ADMIN_API_KEY` and creating named keys, then revoking `bootstrap`. IPv6 peers are bucketed by /64. No aggregate limit is kept: an aggregate bound and "unauthenticated traffic cannot starve the admin caller" exclude each other, and the owner chose the latter. The limiter still forgets buckets when it tracks more than 10000 clients; a source with that many addresses is not bounded by per-client limiting either way.
- [Behind a reverse proxy, all admin callers share one bucket.] The router trusts no forwarded headers. → Accepted and documented.
- [`ADMIN_API_KEY` set to the value of another stored key (D9).] Startup continues and no `bootstrap` key is created or reactivated. If no active admin-tier key exists, nobody can manage keys. → The startup error names the key it collides with; the operator must fix the configuration and restart.
- [Rate limits are per instance.] With N replicas, the effective limits are N times the configured ones. → Accepted and documented.
- [Staleness window.] Another instance can serve a decision up to two intervals old (4s by default). → Bounded and documented. Lower `POLICY_SYNC_INTERVAL` if needed.
- [Fail closed under database trouble.] An instance that cannot reach the database denies all clients after three intervals, even ones it could have answered from the cache. → This is intended. `/readyz` returns `503`, so orchestrators can route around it.
- [Policy edits made by SQL take effect at an unpredictable time (A9).] They are picked up at the next policy reload, which a restart or any admin change or registration triggers. → Documented as unsupported. Use the admin API.
- [The relay name is caller-asserted.] A misconfigured derper can claim a more permissive relay. → Documented trust statement (B3). The derper URL configuration is trusted.
- [`last_used_at` is written on every authenticated admin request.] This adds one write per call. → Admin traffic is low. A failed write must not fail the request.
- [Admin audit growth.] There is no retention. → Retention is a follow-up.
- [`/verify` and `/metrics` are unauthenticated.] Anyone who can reach the port can read a node key's status, exhaust the single global verify rate limit (which, with derper's fail-open off, rejects every client), and grow the verify audit table. → Network access to the port must be restricted; documented. [author, 2026-11-24 fact-check]
- [An operator-tier key can assign any existing role, including one granted on all relays.] → Accepted and documented: give operator keys only to callers trusted with every existing role. [author, 2026-11-24 fact-check]
- [After `bootstrap` is revoked, the configured `ADMIN_API_KEY` stays a dormant admin credential.] A restart reactivates it when no active admin-tier key exists (D3). → Documented: remove or rotate `ADMIN_API_KEY` once named admin keys exist, and keep it secret while set. [author, 2026-11-24 fact-check]
- [The published image is built without cgo and cannot open a sqlite database.] → Documented: the image supports Postgres only; sqlite needs a cgo build. [author, 2026-11-24 fact-check]

## Migration Plan

Upgrade:
1. Archive `harden-registration-and-admin-api` after owner review, so this change's deltas apply to main specs that contain its requirements.
2. Take a database backup. The upgrade revokes devices and changes bindings.
3. Stop every old instance before the first new instance starts. Mixed-version operation is not supported (R6): old instances neither bump nor check the policy version, and their admin writes bypass the version and the audit.
4. Decide the mode of the one-time upgrade (R1/S4):
   - Policy was enforced before: nothing to do. A leftover `enable_casbin: true` is harmless when the data shows registration rules.
   - The previous version ran with `ENABLE_CASBIN=false`: keep that setting for the first start, or set `UPGRADE_POLICY_MODE=disabled`. Either binds every user who is not covered to `standard` and revokes nothing. If the database also holds registration rules (mixed history), `ENABLE_CASBIN=false` alone is refused, so set `UPGRADE_POLICY_MODE`.
   - Startup refused: read the message, which gives the device counts and the contradiction, and set `UPGRADE_POLICY_MODE=disabled` or `UPGRADE_POLICY_MODE=enforced`. Use `enforced` only if policy really was enforced: it revokes every non-revoked device without its registration rule.
   - After the first successful start, remove `UPGRADE_POLICY_MODE`, `ENABLE_CASBIN` and `enable_casbin`. Until then the legacy setting is ignored for enforcement, with a warning, and `UPGRADE_POLICY_MODE` has no effect.
5. Set `ADMIN_API_KEY` for the first start: reviewing the upgrade and re-enabling or binding afterwards needs the admin API.
6. On a large database, start one instance first. Startup has a 30 second limit that includes waiting for the startup lock, so instances started together can time out behind the one that runs the upgrade.
7. Start the new version. It migrates the schema (new tables, plus a relay column on `audit_logs`), seeds `default` and `standard`, runs the one-time upgrade, and creates `bootstrap` from `ADMIN_API_KEY`.
8. Check: read the upgrade warning (users left unbound, devices revoked, rules that grant nothing). `GET /admin/audit/admin` shows the `upgrade.run` row with the mode and counts, and the `system` revocation rows. `GET /admin/users` (with the old `ADMIN_API_KEY`) shows the expected `roles`, and devices that were allowed are still allowed through plain `/verify`.
9. Optional: create relays, roles and named keys, and point additional derpers at `/verify/<relay>`.
10. Deployments that provision by SQL: users and tokens can still be inserted, but such users are denied until bound to a role through the admin API (A9). Policy rows changed by SQL are unsupported and take effect at the next policy reload, at an unpredictable time.

Rollback:
- Stop every new instance before starting the previous version, and keep the backup from step 2 as the last resort.
- Devices registered before the upgrade under enforced policy are still allowed by the previous version, provided their owner still has the `standard` binding. Legacy device rules are kept (R2).
- A deployment that ran with `ENABLE_CASBIN=false` has no registration rules for devices registered while policy was disabled, and must run the previous version with `ENABLE_CASBIN=false` again, or those devices are denied.
- Devices registered under the new version have no registration rule. The previous version denies them with `policy denied` until they register again.
- Rollback can widen access compared with the new version: the previous version re-adds the `standard` grant on `default` at every start, binds `standard` at every registration, lets `/register` reactivate a revoked device (including those the upgrade revoked), evaluates only `default`, and accepts `ADMIN_API_KEY` directly. Named keys stop working.
- New tables and the `audit_logs.relay` column can stay. The previous version ignores them.

## Open Questions

None blocking. These are decisions the owner may want to overrule:

- A6: new users created through the admin API default to role `standard` when `roles` is omitted.
- A8: `ENABLE_CASBIN` is ignored for enforcement, with a warning, rather than failing startup. The one exception is R1/S4: the first start fails when the legacy setting contradicts the data, or when non-revoked devices have no registration rule and the setting is not false, until `UPGRADE_POLICY_MODE` is set.
- C3/C4: other instances reflect a change within two sync intervals, and an instance fails closed after three intervals without a successful check.
- D3: `ADMIN_API_KEY` is both the switch that enables `/admin` and the bootstrap key.
- R1: the upgrade never loosens access, which includes revoking, when policy was enforced, every device without its registration rule, whoever owns it.
- R3: provisioning policy by SQL is unsupported, and SQL changes take effect at the next policy reload, at an unpredictable time.
